# Решения

## ADR-001: Laravel как вторая реализация

Контекст: есть рабочая Python/FastAPI-версия. Нужно проверить, сколько инфраструктуры
заменит Laravel и можно ли сохранить тот же контракт карточки.

Решение: отдельный репозиторий на Laravel 13 / PHP 8.4, пакет `laravel/ai`, без переноса
Python-кода построчно. Контракт карточки и проверки сохраняются, реализация пишется заново.

Следствие: две кодовые базы, которые надо сравнивать по поведению, а не по структуре файлов.
Laravel-версия не считается заменой Python-версии в продакшене, это эксперимент и материал
для цикла статей.

## ADR-002: database-очередь вместо Temporal

Контекст: в Python-версии был Temporal: durable workflow, ретраи, сигналы, replay.

Решение: таблица `card_jobs` со статусами и один Job на шаг. Переход статуса и запись
результата - в одной транзакции с `lockForUpdate`. `ShouldBeUnique` там, где шаг не
переотправляет себя. Human-in-the-loop - это статус в БД, а не спящий Job.

Следствие: нет детерминированного replay. При падении между ответом модели и записью
результата возможен повторный вызов и повторная оплата. Для продакшена нужен идемпотентный
журнал шагов. `retry_after` очереди должен быть больше таймаута Job, иначе воркер заберёт
сообщение повторно.

## ADR-003: Postgres + pgvector вместо отдельной векторной БД

Контекст: нужен и смысловой, и точный поиск по документам, без внешних сервисов.

Решение: `chunks.embedding vector(1024)`, HNSW по косинусу, генерируемый `tsv` с
`to_tsvector('russian', text)`, GIN. Гибридный поиск сливается через RRF.

Следствие: один Postgres хранит и данные, и индекс. На больших объёмах HNSW и GIN надо
тюнить отдельно; `row_number()` по большим спискам дорогой. SQLite для тестов не подходит:
в нём нет `vector` и русского FTS.

## ADR-004: локальные модели

Контекст: CPU-only, около 4.6 ГБ свободной RAM, без GPU. Нужны chat и embeddings.

Решение: Ollama, `gemma3:4b` для генерации, `gemma3:1b` для служебных проверок (детектор
инъекций, судья), `bge-m3` (1024) для эмбеддингов.

Следствие: одна карточка идёт минуты. `gemma3:1b` слишком слаба для критика и судьи:
она выдаёт замечания, которых нет в данных. Это зафиксировано в ADR-007.

## ADR-005: цитата у каждой характеристики

Контекст: ссылка на PDF не проверяема. Ссылка на чанк без проверки значения тоже.

Решение: в контексте короткие метки `S1`, `S2`, …; модель возвращает `characteristics`
массивом объектов `{name, value, chunk_id, page}`; сервер разворачивает метку в настоящий
`chunk_id` и строит `sources`. Проверяются три условия: чанк есть в базе, чанк был в
контексте, значение встречается в тексте чанка. После трёх неудач задача падает.

Следствие: модель должна копировать значения, а не пересказывать. Подстрочная проверка
не ловит синонимы и переформулировки; для характеристик это приемлемо.

## ADR-006: защита контекста и ответа

Контекст: в документах есть PII и prompt injection.

Решение: PII маскируется до и после модели (телефоны, email, карты по Луну, ИНН по
контрольным суммам). Инъекции ищутся правилами и моделью; детектор fail-closed. Если
правило указывает на конкретные предложения, они вырезаются, остаток чанка сохраняется.
Если не осталось смысла или детектор подозревает без конкретики - чанк исключается.

Следствие: вырезание может испортить текст; полный отказ детектора исключает чанк.
Метки `[PHONE_1]` остаются в контексте и ответе, чтобы человек видел факт маскирования.

## ADR-007: критик совещательный

Контекст: шаг `critiquing` должен ловить смысловые ошибки.

Решение: критик остаётся в пайплайне, его вердикт и замечания пишутся в
`guard_report.critique`, но статус карточки от них не зависит. Блокируют схема и проверка
ссылок; низкая уверенность ведёт в `needs_review`.

Следствие: на `gemma3:1b` критик бесполезен, на `gemma3:4b` тоже придумывает замечания.
Это честно записано и в статье, и в README. При появлении сильной aux-модели решение
можно пересмотреть.

## ADR-008: стоимость в микроединицах и evals

Контекст: локальные модели не присылают счёт, но время и токены надо учитывать.

Решение: каждый вызов пишется в `llm_calls`; стоимость хранится целыми микроединицами
по учебному тарифу. `costs:report` группирует по модели и роли. `evals:run` считает
совпадение характеристик, поддержку цитат и вердикт судьи на `golden_cards.json`.

Следствие: тариф не равен реальному прайсу; цифры нужны для сравнения шагов, а не для
бухгалтерии. Судья на слабой модели шумит, поэтому evals - инструмент регресса, а не
сертификат качества.

## ADR-009: `card_jobs` и идемпотентность API

Контекст: Laravel уже занимает таблицу `jobs` под очередь.

Решение: доменная таблица называется `card_jobs`. Создание задачи принимает
`Idempotency-Key`; ключ хранится с уникальным индексом, повторный запрос возвращает
существующую задачу.

Следствие: имена `jobs`/`card_jobs` приходится объяснять. Идемпотентность покрывает
повторный HTTP-запрос, но не повторный вызов модели внутри шага.
